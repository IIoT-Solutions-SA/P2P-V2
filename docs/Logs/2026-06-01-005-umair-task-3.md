## Why This Task Exists

KACST created many forum posts and at least one use case containing scanner/junk payloads. The frontend use-case form has some Zod validation, but backend schemas still accept weak values and malicious-looking text when the API is called directly.

Confirmed backend gap:

- `p2p-backend-app/app/schemas/usecase.py` currently uses plain `str`, `float`, and `List[str]` fields for use case submission.
- A direct schema test accepted values like:
  - `title = "x"`
  - `description = "<script>alert(1)</script>"`
  - `latitude = 999`
  - `longitude = 999`
  - `specificProblems = ["x"]`
- Forum schema is also very loose:
  - `p2p-backend-app/app/schemas/forum.py`
  - `ForumPostCreate.title: str`
  - `ForumPostCreate.content: str`
  - `ForumPostCreate.category_id: str`
  - `ForumPostCreate.tags: Optional[List[str]]`

## Scope

Add backend-enforced validation. Do not rely only on frontend validation.

Primary files/areas:

- `p2p-backend-app/app/schemas/usecase.py`
- `p2p-backend-app/app/schemas/forum.py`
- `p2p-backend-app/app/api/v1/endpoints/usecases.py`
- `p2p-backend-app/app/api/v1/endpoints/forum.py`
- Optional shared helper, e.g. `p2p-backend-app/app/core/input_validation.py`

## Required Use Case Backend Validation

Mirror or improve the current frontend rules from `p2p-frontend-app/src/pages/SubmitUseCase.tsx`.

Recommended backend constraints:

- `title`: 10–100 chars
- `subtitle`: 10–150 chars
- `description`: 50–5000 chars
- `category`: must be one of the allowed use-case categories
- `factoryName`: 2–80 chars
- `city`: 2–50 chars
- `latitude`: -90 to 90
- `longitude`: -180 to 180
- `industryContext`: 50–5000 chars
- `specificProblems`: 2–5 items; each 10–500 chars
- `financialLoss`: 5–500 chars
- `selectionCriteria`: 2–5 items; each 10–500 chars
- `selectedVendor`: 2–120 chars
- `technologyComponents`: 1–15 items; each 20–500 chars
- `implementationTime`: 3–120 chars
- `totalBudget`: 3–120 chars
- `methodology`: 20–5000 chars
- `quantitativeResults`: 2–4 items; validate metric/baseline/current/improvement lengths
- `challengesSolutions`: 1–4 items; validate challenge/description/solution/outcome lengths
- `contactPerson` / `contactTitle`: optional, max 120 chars
- `images`: max 5; only accepted media URLs/paths from allowed upload flow/storage

Also apply safe constraints to optional extended sections where practical:

- `industryTags` / `technologyTags`: max 10 each; each tag 2–30 chars; safe characters only
- `vendorProcess`, `vendorSelectionReasons`
- `projectTeamInternal`, `projectTeamVendor`
- `phases`
- `qualitativeImpacts`
- `technical_architecture`
- `future_roadmap`
- `lessons_learned`

Draft endpoint note:

- `UseCaseDraftCreate` can be partial, but when a field is provided it should still pass length/safety validation.
- Publishing/submitting must enforce the full required validation.

## Required Forum Backend Validation

- Forum post `title`: 8–150 chars
- Forum post `content`: 20–5000 chars
- Forum reply/comment `content`: 2–3000 chars
- `category`: normalized and restricted to known categories where possible
- `tags`: max 5; each 2–30 chars; safe characters only
- attachments: max 5 and only allowed uploaded media URLs/metadata

## Security Payload Rejection

Reject obvious scanner/injection payloads in plain-text fields, including:

- `<script`, `</script`
- `javascript:`
- `onerror=`, `onload=`, `onclick=` and similar HTML event handlers
- path traversal like `../`, `..\\`, `/etc/passwd`
- null bytes/control characters
- `oastify.com` / known collaborator-test strings
- XXE/XInclude probes like `<!DOCTYPE`, `<xi:include`, `xsi:schemaLocation`
- SSI probes like `<!--#exec`, `<!--#echo`, `<!--#set`
- LDAP/objectClass injection patterns

Allow normal Arabic/English business text, punctuation, numbers, and ordinary links where appropriate.

## Acceptance Criteria

- Invalid direct API payloads return `422` or `400`; they must not be saved.
- Normal valid forum post, forum reply, use case submit, and use case draft save still work.
- Add tests if the project test setup is usable; otherwise include documented curl/API proof in the PR notes.
- Keep error messages clear enough for the frontend/user to understand what failed.
- Open PR into `hamza-backend`.

## Notes

This task is deliberately backend-focused. The frontend already has some use-case validation, but KACST can bypass frontend validation by calling the API directly.
